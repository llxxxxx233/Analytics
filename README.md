# 衍生品经营分析 Agent
### AI-Powered Merchandise Analytics & Planning Assistant

> 面向二次元 IP 衍生品运营场景的 AI 数据分析与决策辅助工具，帮助个人创作者及小型周边经营者整理销售数据、识别商品表现、分析库存风险，并为下一期商品企划提供数据支持。

**项目类型：** 个人实践项目 / AI 应用开发
**应用场景：** 二次元 IP 衍生品、电商运营、商品企划与库存管理
**技术栈：** Python、Pandas、Streamlit、Plotly、大语言模型 API
**项目状态：** 开发中 —— 数据整理、经营看板与 AI 数据洞察已实现并可部署；备货情景分析与报告导出待完成

---

## 1. 项目背景

二次元 IP 衍生品经营不仅涉及设计与生产，还需要在商品选择、定价、备货、渠道销售和库存管理之间进行权衡。

在个人周边运营实践中，销售记录可能分散在微店订单、展会记录和日常表格中。由于缺乏统一的数据整理与分析流程，经营者往往难以快速回答以下问题：

- 哪些商品在现有销售记录中表现较好？
- 不同品类、商品和销售渠道的表现有什么差异？
- 哪些商品可能存在库存积压或补货不足的风险？
- 在预算有限的情况下，下一期应该优先考虑哪些商品？
- 如何将零散的经营记录转化为可执行的企划建议？

传统 Excel 表格能够完成基础统计，但需要经营者自行整理数据、编写公式并解释分析结果。大语言模型可以辅助理解业务问题、生成分析报告，但如果缺乏可靠的数据计算与约束，也可能产生不准确的数字或缺乏依据的建议。

因此，本项目尝试将**结构化数据分析与大语言模型的业务理解能力相结合**，构建一个轻量级的衍生品经营分析 Agent。

## 2. 项目目标

本项目围绕“数据整理—经营分析—问题诊断—企划建议”构建分析流程，目标包括：

1. **降低数据整理成本：** 将订单、商品和库存等数据统一为可分析的数据结构。 ✅
2. **提高经营分析效率：** 通过交互式图表展示商品销量、销售额及品类表现。 ✅
3. **辅助运营决策：** 结合历史表现、库存和成本信息，识别值得关注的商品与经营风险。 🔄（库存风险已实现，备货方案待做）
4. **实现自然语言交互：** 允许用户通过业务问题获取数据分析结果和解释。 ✅
5. **提高建议的可验证性：** 让关键指标由代码计算，分析结论能够追溯至数据和计算口径。 ✅

本项目定位为决策辅助工具，而非自动替代经营者完成选品、定价和采购决策的系统。

## 3. 核心功能

### 3.1 智能数据导入与预处理 ✅ 已实现

支持导入商品信息、订单明细和库存记录等结构化数据，并对不同来源的数据进行统一处理。

主要功能：

- Excel / CSV 文件上传。
- 字段识别与数据格式标准化（中英文列名自动映射）。
- 商品名称、品类、日期及渠道等字段清洗。
- 缺失值、重复记录和异常数据检查。
- 数据质量报告与字段完整性提示。

对于缺少成本、库存或历史时间记录的数据，系统应明确提示其影响，不将未知值自动当作零值，也不通过大模型生成虚构的历史记录。

### 3.2 商品经营分析看板 ✅ 已实现

基于清洗后的数据，通过交互式可视化展示商品和品类的经营表现。

| 分析维度 | 核心指标 | 分析目的 |
|---|---|---|
| 销售表现 | 销量、销售额、订单数 | 识别当前记录范围内表现较好的商品 |
| 品类表现 | 各品类销量及销售额占比 | 比较不同商品类型的表现 |
| 时间趋势 | 日 / 周 / 月销售趋势 | 观察销售变化与活动节点 |
| 渠道表现 | 各渠道销售额与销量 | 比较线上与线下的可观测表现 |
| 库存分析 | 当前库存、库存覆盖天数等 | 在数据充分时识别潜在库存风险 |

所有指标根据实际可用字段计算。未提供完整订单或渠道记录时，系统应显示统计范围与数据限制，避免将局部记录误认为全部经营结果。

### 3.3 AI 经营分析与对话式洞察 ✅ 已实现

用户可以使用自然语言提出经营分析问题，例如：

- “本月哪些商品的销售表现最好？”
- “不同品类的销售额有什么差异？”
- “哪些商品值得在下一期企划中继续关注？”
- “目前有哪些数据不足以支持补货决策？”

**实现方式：** 系统根据问题识别所需指标，调用对应的数据查询与计算模块，把计算结果组装为一段“数据上下文”，再由大语言模型对计算结果进行解释，输出**结论 → 依据（引用具体数字）→ 可执行建议**。

同时支持**商品营销话术**：选择任意商品，基于其真实销量、销售额、均价等信息生成 2~3 种风格的种草文案（朋友圈 / 商品详情 / 社群推广）。

设计原则：

- **先计算，后解释：** 销量、销售额及比率等关键指标由 Python 计算。
- **有据可查：** 分析结论关联相应指标、数据范围和计算口径。
- **明确不确定性：** 数据不足时说明缺少什么信息，以及为什么无法得出确定结论。
- **避免因果过度推断：** 销量差异只能说明观察到的销售表现不同，不能直接证明某种设计或渠道必然导致销量提升。

### 3.4 库存风险与备货情景分析 🔄 部分实现

**已实现：** 在商品销量、当前库存等必要数据可用时，识别库存偏高、销售缓慢或可能缺货的商品，并根据历史销售速度估算库存覆盖天数。

**待实现：**

- 比较不同备货数量下的资金占用与潜在库存风险。
- 在给定预算、最低起订量等约束下，生成备货方案供用户评估。

对于没有真实库存和成本记录的历史商品，可以使用明确标注的模拟数据演示功能，但不将模拟结果描述为实际经营结论。

### 3.5 自动生成经营分析报告 ⏳ 待实现

将指标计算、图表和 AI 分析结果整合为结构化报告。

报告内容包括：

1. 本次分析的数据范围与质量说明。
2. 核心经营指标及趋势。
3. 表现较好的商品与值得关注的异常。
4. 库存和备货风险（仅在数据支持时生成）。
5. 下一期企划建议及其依据。
6. 需要补充的数据和建议的后续验证方式。

## 4. 系统架构

```text
用户上传文件 / 输入业务问题
             |
             v
    数据导入与质量检查
             |
             v
      Pandas 数据处理
             |
             v
    指标计算与数据查询
             |
             v
    数据上下文组装（Insights）
             |
             v
    大语言模型分析与解释
             |
             v
    图表展示 / 运营报告 / 企划建议
```

系统采用模块化设计，将数据处理、指标计算、大模型调用和前端展示分离。

| 模块 | 主要职责 |
|---|---|
| Data Loader | 文件读取、字段映射与数据导入 |
| Data Validator | 缺失值、重复记录和数据质量检查 |
| Analytics Engine | 销售统计、趋势分析和库存指标计算 |
| Insights Builder | 将计算结果组装为给大模型的“数据上下文” |
| LLM Service | 业务问题理解、结果解释、建议与营销话术生成（OpenAI 兼容接口） |
| Report Generator | 整合指标、图表和分析文本（待实现） |
| Streamlit UI | 文件上传、交互式查询和结果展示 |

大模型不直接决定关键指标的数值。涉及金额、数量、比率和约束计算的任务优先交由确定性的代码执行。

## 6. 数据设计与真实性说明

本项目优先使用个人周边运营过程中能够核实的历史资料，并将历史数据与模拟数据严格区分。

### 6.1 数据来源

- 商品信息：商品名称、IP、品类及规格等。
- 订单信息：订单日期、商品、数量、成交金额及销售渠道等。
- 库存信息：仅在有可靠记录时使用。
- 成本信息：仅在有历史凭证或可核实依据时使用。

### 6.2 数据分类

| 数据类型 | 使用方式 | 展示要求 |
|---|---|---|
| 真实历史数据 | 经营分析与案例复盘 | 说明来源、范围与统计口径 |
| 整理还原的数据 | 从现有订单或凭证重新汇总 | 说明整理规则与缺失项 |
| 模拟数据 | 功能测试、交互演示和情景分析 | 显著标注“模拟数据”，不得冒充历史业绩 |

- 真实脱敏数据放在 `data/raw/`（已加入 `.gitignore`，**不提交**）。
- 模拟数据放在 `data/sample/`（演示用，界面中会显著标注）。
- 个人订单、客户信息和合作方信息应在展示前脱敏。公开项目中不提交真实个人信息、订单明细或 API 密钥。

## 7. 评估与验证方案

项目不仅关注界面是否能够运行，还关注计算是否正确、建议是否有依据。

### 7.1 数据处理验证 ✅（pytest 已覆盖部分）

- 检查重复订单与异常字段的处理结果。 ✅
- 使用人工核算的小样本验证销量和销售额。 ✅
- 验证不同日期范围、品类和渠道筛选条件下的结果。 ⏳
- 检查缺失字段是否导致不合理的指标输出。 ✅

### 7.2 AI 输出验证

- 核对报告中的关键数字是否与计算结果一致。
- 检查结论是否超出数据实际支持的范围。
- 测试信息不足时是否能够主动说明限制。
- 检查建议是否满足用户给定的预算和备货约束。

以上通过系统提示词约束（数字不得编造、数据不足须说明、禁止因果过度推断），并在交互中人工核验。

### 7.3 运营建议验证 ⏳

使用若干具有代表性的商品案例，对比：

- 仅展示原始数据时，经营者需要自行完成的分析。
- 引入自动化指标计算与 AI 解释后的分析结果。
- 在不同库存、预算和需求假设下，建议是否发生合理变化。

在完成实际测试之前，不预设准确率、效率提升比例或商业收益等实验结果。

## 9. 本地运行

### 9.1 环境准备

建议使用 Python 3.11 或与所选依赖兼容的版本（本项目在 Python 3.14 下开发验证）。

```bash
git clone <your-repository-url>
cd <repository>

python -m venv .venv
```

激活虚拟环境后安装依赖：

```bash
# Windows
.venv\Scripts\activate

# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

### 9.2 配置模型 API

在本地 `.env` 文件中配置大模型服务（`.env` 已加入 `.gitignore`，不会提交）。以智谱 GLM 为例：

```text
LLM_API_KEY=your_api_key
LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
LLM_MODEL=glm-4-flash
```

本项目的 LLM 服务走 OpenAI 兼容接口，替换 `LLM_BASE_URL` 与 `LLM_MODEL` 即可切换到 DeepSeek、通义等其他兼容服务。

### 9.3 启动应用

```bash
streamlit run app.py
```

启动后，根据页面提示上传符合字段要求的数据文件（或使用内置模拟数据），查看数据质量检查结果，再进行销售分析或 AI 问答。

部署到 Streamlit Cloud 的步骤见 [DEPLOY.md](DEPLOY.md)。

## 11. 项目价值与后续方向

本项目尝试将个人周边运营实践与数据分析、生成式 AI 相结合，探索如何降低小型商品经营场景中的数据整理成本，并提高经营分析的可解释性与可执行性。

项目重点不在于简单地将大模型接入聊天界面，而在于建立一条可验证的工作流：从原始经营数据出发，经过标准化处理和确定性计算，再由 AI 解释结果、识别信息缺口并辅助形成运营建议。

后续可以进一步探索：

- 多 IP、多品类商品的统一经营分析。

- 结构化分析报告的一键导出。
